# Module 2 security notes

**Implemented in source:** OAuth authorization code flow, state cookie + server-side one-time state, PKCE S256, explicit single-account allowlist, restricted `gmail.modify` scope, encrypted OAuth token storage with AES-256-GCM, encrypted draft content, recipients and attachments, hashed random session cookies, HttpOnly cookies, SameSite=Lax, Secure cookies on HTTPS production, session expiry, same-origin CSRF protection for mutations, no-store responses, header injection rejection, bounded fields/attachments, server-side draft versions and content fingerprints, explicit one-time approval, atomic database send reservation and no automatic retry on uncertain send, Google API-confirmed message IDs, account/session/draft deletion.

**Never commit:** `backend/.env`, `backend/private/`, database backups, client secrets or OAuth tokens. `.env.example` is placeholders only. Protect encryption keys and disk backups separately; losing an encryption key loses token/attachment recoverability.

**Application deployment:** `NODE_ENV=production`, HTTPS origin, strictly configured OAuth redirect URI, Google account allowlist, restricted reverse proxy, security patches, reasonable rate limits/WAF, CSP (requires deployment-specific nonce policy), log scrubbing, encrypted disk, vault/secret manager, private DB directory, regular rotation/backup plan. Single SQLite DB is intended for **one backend instance**, with a persistent disk. Horizontal replication requires a proper shared transactional datastore and distributed locking, not independent SQLite files. Node's built-in `node:sqlite` requires Node 22.13+ and is experimental in this runtime; pin and test the Node release.

**Privacy:** Real email bodies are not stored in browser localStorage. Real messages are in memory during use; demo content and user settings stay in the existing localStorage namespace. User email content is untrusted: React only displays it as text, never executable HTML. AI text generation remains disabled for live mail in Module 2. The Activity page's live entries are local session events, **not a complete audit log**; persisted draft state/send receipt are in the backend.

**Remaining risk / not production hardened:** no deployment-ready rate limiter or cloud secrets manager, no Google verification or restricted-scope assessment, no browser-tested CSP, no comprehensive MIME charset parser, no virus scanning on uploads, no multi-instance locking, no background worker, no alerting/incident response, no full route-level Express integration tests in this offline environment. Treat this as a security-conscious integration implementation requiring final environment validation and hardening, not a certified production service.
